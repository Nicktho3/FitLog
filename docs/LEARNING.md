# Learning FitLog: follow the code, one request at a time

This guide explains the implementation added to your original project. Read it with the named source file open. Line references below refer to this version; blank lines simply separate related blocks. Repeated fields and styling rules are grouped so you learn the pattern rather than memorize every repetition.

## 1. Start with one action: “Log food”

Suppose you enter Chicken and rice, 520 calories, 40 g protein, 60 g carbs, and 15 g fat.

1. **HTML** gives each input a `name`, such as `calories`. These names become JSON keys.
2. **JavaScript** catches the form's `submit` event. `event.preventDefault()` prevents the browser's normal page reload.
3. `FormData(form)` collects input values. `Number(...)` converts numeric strings into numbers.
4. `fetch('/api/foods', ...)` sends a POST request containing the values and chosen date. The browser includes the session cookie automatically.
5. **FastAPI** matches that URL to `add_food` and validates the JSON with `FoodCreate`.
6. `Depends(current_user)` verifies the cookie and finds the signed-in account. `Depends(get_db)` supplies a database session.
7. **SQLAlchemy** builds a Food row, assigns its owner on the server, and commits it.
8. FastAPI sends the saved food back as JSON, including its database-generated ID.
9. JavaScript calls `loadDay()` to get fresh totals and renders the updated food list.

The browser never connects directly to SQLite or PostgreSQL. It asks the backend to perform a specific operation.

## 2. Database connection — `Backend/database.py`

| Lines | What the code does and why |
| --- | --- |
| 1–6 | The docstring describes the module. `os` reads environment variables, `Path` constructs filesystem paths, and SQLAlchemy imports provide the database tools. |
| 8 | `Path(__file__)` starts from this file. `.resolve()` makes it absolute; two `.parent` accesses find the repository root. This avoids depending on where the shell was opened. |
| 9 | `os.getenv` uses `DATABASE_URL` if supplied; otherwise the f-string builds a SQLite URL pointing to `fitlog.db`. |
| 10–13 | `create_engine` constructs the connection manager. SQLite's `check_same_thread=False` allows connections to be used by FastAPI's worker threads. This does not mean sharing one Session across requests is safe. |
| 14 | `sessionmaker(bind=engine)` creates a factory: calling `SessionLocal()` makes a database session. |
| 15 | `declarative_base()` creates the parent class that all table models inherit from. Its metadata remembers the table definitions. |
| 18–21 | `get_db` opens a session inside `with`. `yield db` lends it to the request; after the request, execution resumes and `with` closes it, including when the request fails. |

**Connection, session, and login session are different things.** The engine manages database connections. A SQLAlchemy Session coordinates queries and transactions. The `LoginSession` table represents a user's authenticated browser session.

## 3. Table definitions — `Backend/models.py`

Each `class Something(Base)` describes a table. Each `Column(...)` describes one field in that table.

- `__tablename__` names the actual SQL table.
- `Integer`, `Float`, `String`, and `Date` choose storage types.
- `primary_key=True` uniquely identifies a row. Integer IDs are generated by the database.
- `nullable=False` disallows SQL NULL; it does not validate a blank string. Input validation handles that.
- `unique=True` prevents duplicate values at the database level, including concurrent requests.
- `ForeignKey('users.id')` describes a reference to a user. Ownership is still enforced by our route filters. SQLite foreign-key enforcement is not enabled here, and the app has no user-deletion feature.
- `index=True` creates an index that can speed up filtering, with some extra storage/write cost.

| Class | Field-by-field explanation |
| --- | --- |
| `User` | `id` identifies the user. `email` and `username` are required and unique. `hashed_password` stores a one-way password hash, never the original password. This preserves your existing table's shape. |
| `LoginSession` | `token_hash` is the primary key. `user_id` identifies the owner. `expires_at` stores an absolute expiry time in seconds since the Unix epoch. A user can have multiple browser sessions. |
| `Food` | `id` identifies the entry; `user_id` owns it; `date` selects its journal day; `name` describes the food. The four numeric columns store entered portion totals. Calories are entered independently, not derived from macros. |
| `Workout` | The first three columns serve the same purpose as Food. `exercise` is its name. `sets` and `reps` store counts; `weight` stores pounds per set. Three sets of eight at 135 lb is one row. |
| `Goal` | `user_id` is the primary key, giving each user at most one goal row. The four values have defaults used when the row is inserted. Defaults are illustrative and editable. |

The models describe **storage**. The next file describes **what clients may send and receive**. Those are separate responsibilities.

| Lines | Explanation |

| 7 | `Name` is a reusable string type limited to 1–120 characters. |

| 26–27 | `UserCreate` inherits email/password from `UserLogin` and adds a username. Its regex permits letters, digits, underscores, and hyphens. Unlike your original schema, registration does not ask the browser for a database ID. |

| 46–48 | `FoodResponse` inherits food fields, reads ORM attributes, and adds the generated ID. |

## 5. Authentication — `Backend/auth.py`

| Lines | Explanation |
| --- | --- |
| 2–14 | `hashlib` hashes bytes; `hmac` provides a timing-resistant digest comparison; `secrets` generates unpredictable values; `time` provides expiry timestamps. `bcrypt` is retained solely to verify hashes from your earlier prototype. FastAPI and model imports connect this module to requests and storage. |
| 16–18 | Constants name the cookie, set a seven-day lifetime, and set PBKDF2's work factor. Underscores in `600_000` improve readability without changing its numeric value. |
| 21–22 | Generate a fresh random salt for every password. Two people with the same password should not have the same stored hash. |
| 23 | `.encode()` turns text into bytes. PBKDF2 repeatedly applies HMAC-SHA256 to make password guessing more expensive. |
| 24 | Store algorithm, work factor, salt, and digest in one `$`-separated string. These parameters are needed to verify the password later. The hash is not reversible encryption. |
| 27–31 | Recognize bcrypt prefixes and use the bcrypt library to verify old hashes. New accounts use PBKDF2. |
| 32–36 | Split a PBKDF2 record, check the algorithm, recompute the candidate password using the stored salt/work factor, and compare the two digests. |
| 37–38 | A malformed stored hash returns `False` instead of crashing the login route. |
| 41–42 | Session tokens are already high-entropy random values, so a fast SHA256 digest is suitable for database lookup. Passwords need an intentionally slower algorithm because people choose predictable passwords. |
| 45–46 | Generate a fresh session token from 32 random bytes on successful registration/login. |
| 47 | Delete expired sessions while creating a new one, keeping expired records from accumulating indefinitely. |
| 48–50 | Store only the token's hash, owner, and expiry, then commit. A database record alone does not reveal the original bearer token. |
| 51–53 | Send the raw token in a cookie. `httponly` prevents JavaScript from reading it. `samesite='strict'` restricts cross-site sending. `secure` requires HTTPS when enabled. `max_age` gives the browser the same session lifetime. |
| 56–58 | Read the cookie, hash it, and look up the session. No cookie means no authenticated session. |
| 59–60 | Reject missing or expired sessions with HTTP 401. |
| 61–64 | Retrieve the owner, reject a missing account, and return the authenticated User object to the route. |

Knowing an account's ID is not enough to sign in. The server requires the unpredictable token. Logging out deletes the database record, so even a copied old cookie stops working.

The core database write, line by line:

```python
@app.post("/api/foods", response_model=schemas.FoodResponse, status_code=201)
def add_food(data: schemas.FoodCreate, user=Depends(current_user), db: Session = Depends(get_db)):
    food = models.Food(user_id=user.id, **data.model_dump())
    db.add(food)
    db.commit()
    db.refresh(food)
    return food
```

- `@app.post(...)`: register the URL, HTTP method, output schema, and success status.
- `def add_food(...)`: define the function and its validated/injected inputs.
- `models.Food(...)`: construct a Python object representing one table row.
- `user_id=user.id`: obtain ownership from authenticated server state, not submitted data.
- `**data.model_dump()`: unpack the validated dictionary into keyword arguments, equivalent to `date=data.date, name=data.name, calories=data.calories, ...`.
- `db.add(food)`: mark the new object for insertion; it is not saved permanently yet.
- `db.commit()`: complete the transaction and persist the insert.
- `db.refresh(food)`: read database-generated values back into the object.
- `return food`: let FastAPI serialize the object according to `FoodResponse`.

## 8. Page structure — `Frontend/index.html`

Read the HTML from the outside inward:

- `<!DOCTYPE html>` requests modern HTML behavior; `lang="en"` identifies the page language.
- Charset and viewport metadata support text encoding and mobile sizing.
- The stylesheet link loads presentation rules. The script's `defer` waits until HTML has been parsed before code looks for its elements.
- The header contains the brand and a hidden account area, which JavaScript reveals after sign-in.
- `main` holds a `role="status"` live message for loading/errors and the two main sections.
- `#auth` contains the introduction and login/register form. Wrapping inputs in labels associates visible names with controls. The username field starts hidden and disabled for login.
- `#journal` starts hidden. Its date input controls which day's records the API returns.
- Four summary cards provide separate elements for totals and goals; JavaScript updates them by ID. Native `progress` handles the calorie bar without a chart library.
- Food inputs use names that match `FoodCreate`. Numeric `min`, `max`, and `step` offer browser validation; the server remains authoritative.
- Workout inputs match `WorkoutCreate`, and visible instructions explain pounds and the “same reps/weight per row” model.
- Empty `ul` elements are filled by `renderEntries`. We do not keep duplicate hard-coded entries in HTML.
- `details` and `summary` provide a keyboard-accessible expandable goal editor using native browser behavior.
- The final note explains date history and how to correct entries, followed by a small footer.

`id` identifies one DOM element; `class` groups elements for styling; `name` identifies a form field sent to the server. They are related but not interchangeable.

## 10. Tests and supporting files

In `tests/test_api.py`, the `database` fixture creates a fresh SQLite file inside `tmp_path` and creates its tables. `app.dependency_overrides[get_db]` replaces the real database dependency with the test one. `yield` hands it to the test, then cleanup restores dependencies and disposes the engine. Tests therefore cannot overwrite your journal database.

The `client` fixture sends HTTP requests directly to FastAPI with `TestClient`; no listening server is required. It deliberately does not run the production lifespan, since its isolated schema was already created. `register` is a helper that keeps account setup short.

- `test_account_lifecycle`: checks unauthorized access, safe response fields, cookie flags, hashing, revocation of a copied cookie, email normalization, invalid login, and duplicate registration.
- `test_logging_totals_history_and_delete`: creates food/workout entries, verifies summed macros and date filtering, updates goals, removes entries, and verifies saved data after a fresh login.
- `test_users_cannot_read_or_delete_each_others_entries`: creates two users and proves that ownership filters apply to reads, deletes, and goals.
- `@pytest.mark.parametrize`: runs the validation test once per bad payload, covering invalid dates/names/numbers and attempted ownership injection.
- `test_session_expiry`: changes the stored expiry to the past and expects 401.
- `test_security_and_static_files`: checks the served frontend, required authentication, JSON-only writes, cross-site rejection, and framing policy.
- `test_password_whitespace_is_preserved`: proves spaces are part of the password rather than silently stripped.
- `test_legacy_bcrypt_account_receives_goals`: creates a prototype-style user and verifies compatibility.
- `test_reject_invalid_account_and_goals`: checks invalid email/password, zero calorie goals, and malformed date queries.

The optional `docs/github-actions-tests.yml` template can be copied to `.github/workflows/tests.yml` when your GitHub credentials permit workflow changes. It is not active CI yet. In that template, `on` selects pushes and pull requests. `jobs` defines an Ubuntu runner. Checkout downloads the repository; setup-python selects Python 3.12; pip installs dependencies; pytest runs the tests; `node --check` validates JavaScript syntax. A failed command fails the job.

`requirements.txt` pins direct runtime dependencies. `requirements-dev.txt` includes those and testing packages. `requirements-lock.txt` captures transitive packages too, making the tested environment reproducible. `.gitignore` excludes virtual environments, credentials, local databases, and test caches from commits. `.env.example` is safe configuration documentation, not real secrets.

## 11. Things to be ready to explain in an interview

1. **Why FastAPI?** Type-driven request validation, straightforward routes, and generated API documentation.
2. **Why plain JavaScript?** The app is small enough to learn DOM and HTTP fundamentals without a frontend framework.
3. **Why SQLite by default?** It removes setup friction for reviewers; SQLAlchemy also supports the optional PostgreSQL configuration.
4. **How is ownership protected?** Every data query is scoped by the user recovered from a validated server-side session.
5. **How do you know it works?** Integration tests exercise the HTTP interface against isolated real database tables; manual browser checks cover the rendered workflow.
6. **What would you improve before public hosting?** Rate limiting, password reset/email verification, migrations, backups, HTTPS configuration, and more operational monitoring.

## 12. Learn by changing one thing

Start with an exercise you can finish without copying a full solution:

1. Find the HTML placeholder for exercise and change it. Reload. This demonstrates static asset serving.
2. Add one more food for the same date and predict every total before submitting. Inspect the `/api/day` response in the browser's Network panel.
3. Change the test's calories from 520 to 600 and predict the new expected total. Run the suite; adjust the assertion to match the behavior you intended.
4. Add a workout notes field. Before coding, list which of models, schemas, routes, HTML, JavaScript, tests, and database migrations would need changes and why.

Being able to trace, test, and modify one feature is more useful than memorizing this file.
